# Chit Bot pre-deployment audit

**Scope:** the Telegram bot on branch `feat/chit-bot` at commit `27ef1cb`: `src/fleet/bot-runtime.ts`, `bot-handlers.ts`, `bot-wallets.ts`, `bot-chain.ts`, `bot-fleet.ts`, `bot-telegram.ts`, `api/bot.js`, `scripts/bot-set-webhook.mjs`, and their tests. The hosted fleet service and the contracts are out of scope except where the bot's assumptions about them were wrong.
**Date:** 2026-09-16, before any deployment: no wallet exists yet, so every fix could change the storage format freely.
**Method:** ten independent readers, one lens each (key custody, webhook and auth, money bounds, concurrency and state, the chain adapter, the fleet driver, honesty of the copy, runtime configuration, the SQL store, test gaps), over the sources and the service they call. 89 findings, 86 after de-duplication by file and line. Each finding then went to three adversarial judges (one told to refute it, one to trace the path line by line, one to size the impact); a finding stood when fewer than two judges refuted it. The first 25 findings got all three judges and all 25 stood; the session's model budget ran out before the other 61 were judged, so those were traced by hand against the code and the service, and turned out to be either duplicates of the judged ones or real. Nothing below was accepted on a reader's word alone. Every fix carries a test that failed before it.
**Purpose:** the bot holds testnet keys for other people and moves their test ETH on a tap. Nothing here is real money, and that is exactly why it had to be audited now: the mainnet bot will not hold keys, but it will inherit this code's habits.

Severity: **High** = keys or funds cross users, or an unauthenticated path signs; **Medium** = a user is charged or traded twice, a guarantee in the docs is false, or a card lies; **Low** = robustness; **Info** = worth knowing.

---

## Threat model

| Party | Can | Cannot |
|---|---|---|
| Anyone on the internet | POST to `/api/bot` | know the webhook secret, the sealing secret, or the Neon URL |
| A user | tap any button, type any reply, replay old cards, run many Telegram clients at once | reach another user's `tg_id` in a request Telegram signs |
| Telegram | redeliver any update, deliver one update to two function instances, drop a reply | forge a secret header |
| Someone with a database dump | read every row | know the sealing secret |
| The operator | everything, including the secrets | nothing they should not: the point of the design is that a dump plus a guessed secret is worthless |

Vercel runs the webhook as many function instances with no shared memory. Every guarantee that lived in an instance's memory was false on the hosted bot; the store is the only shared thing.

## Findings and fixes

### F1 · High · The webhook failed open without its secret

`handleBotRequest` compared the `X-Telegram-Bot-Api-Secret-Token` header only `if (secret && …)`, and `getBot()` did not treat a missing `TELEGRAM_WEBHOOK_SECRET` as a fault, while the header comment, the setWebhook script and the docs all said the secret was checked on every update. The script demanded the secret on the operator's laptop, not on the host: a deployment without the variable served every POST as a genuine update. `#callback` takes `tgId` from the body, so `{"callback_query":{"data":"w:<attacker>:0.019","from":{"id":<victim>},…}}` opened the victim's sealed key and signed a send; the same forgery drove buys, sells and deposits, and forged `/start` messages for invented ids drained the faucet. Judged by three, confirmed by all.

**Fixed:** the runtime refuses to build without a 16+ character secret; the request handler compares in constant time and answers 403 to any request without the exact header, secret variable or not. `test/fleet/bot-runtime.test.ts`.

### F2 · High · Whole-row upserts from stale objects erased the fleet and rolled the faucet back

`store.put(wallet)` wrote every column from an object the handler had read earlier. A settings change on one instance while another had created a fleet wrote `fleet = NULL`, losing the campaign id and the five sealed fleet keys; overlapping taps rolled `faucet_at` back and re-armed the once-a-day faucet. Judged, confirmed.

**Fixed:** there is no `put`. `create` is insert-if-absent and returns the stored row (the first writer's on a race, so the loser carries on with the wallet that exists and does not faucet a phantom); `patch` updates one column at a time; the faucet stamp is claimed atomically. `test/fleet/bot-wallet-store.test.ts`, run over the memory store, the Neon store on PGlite, and Neon when a scratch database is named.

### F3 · High · Confirm trades and sell protection were bypassed by the card's own buttons

The token card emitted `bc:`/`sc:` (the already-confirmed verbs) when confirm trades was on, and Positions wired "Sell 100%" to `sc:` unconditionally. Any old card, or a user who turned the setting on after the card was drawn, traded without the step they had asked for.

**Fixed:** every card button carries the plain verb; the handler alone decides whether to ask. `chit-bot.test.ts`: "applied by the handler whatever button was pressed".

### F4 · High · The fleet dead-ended after create, and ended fleets looked new

`fleetPhase` mapped the service's real post-create state, `Awaiting funding`, to "activating" (no activate button, ever), and `Revoked`, `Depleted` and `Expired` fell through to "created" (an activate button that always 409s, and no close). The status card read `budget` and `accounts` fields the real status route never returns (it returns `state` and `draw`), and the first path the card suggested, deposit 0.01 then draw 0.02, was refused by the service as `insufficient_balance`. The service also keeps an un-activated campaign only in the instance that created it, so a bot that created on one tap and activated on the next could meet `campaign_unknown` after a redeploy.

**Fixed:** phases follow `campaign-state.ts` by name; ended fleets offer close; the status card reads the draw; the draw menu offers only sizes the pool balance covers, read from the service at tap time; create, confirm and activate are one tap; a fleet that did get created but not activated can be activated later or forgotten (it holds no money), and a fleet with a draw open is never overwritten. `fleetPhase` unit test and two fleet journeys in `chit-bot.test.ts`.

### F5 · Medium · Sealed keys were not bound to their row, the derivation was one hash, and a rotated secret failed silently

AES-GCM with no associated data: a database writer could move a sealed key under another `tg_id` and have the bot decrypt and sign with it. The key was `sha256("…|" + secret)` of any 32-character string, so a dump plus a guessable secret was a fast offline attack. No key id in the blob and no canary: a mistyped or rotated `BOT_KEY_SECRET` made every open fail as a bad tag while Start kept making new wallets. The fleet record (campaign id, fleet addresses, sealed keys) sat in plaintext JSON, handing a dump the Telegram-id-to-fleet mapping the product exists not to publish.

**Fixed:** scrypt (N=2^15) derives the key once per instance; every blob carries associated data `<tgId>|wallet`, `<tgId>|fleet-key` or `<tgId>|fleet`; the blob starts with four bytes naming the sealing key so a mismatch is reported as such; a canary row in `bot_meta` is checked once per instance and the bot refuses to serve on a mismatch; the fleet record is sealed whole; the runtime refuses a secret with fewer than twelve distinct characters. Tests: sealing, "a rotated sealing secret stops the bot".

### F6 · Medium · No update dedupe, and money guarded per instance only

Telegram redelivers an update that was not answered in time or whose handler crashed, and Vercel may answer one update on two instances. The bot re-executed buys, sells, withdrawals and deposits on redelivery, and the "one trade at a time" set lived in one instance's memory, so the documented nonce guarantee did not hold on the hosted bot. Fleet idempotency keys were random per call, so a retry was a new action to the service.

**Fixed:** `update_id` is claimed in the store before anything runs; every money path takes a store-held lock per wallet (ninety-second lease, released in `finally`, past the function's sixty seconds); fleet idempotency keys derive from the Telegram callback id. `vercel.json` gives `api/bot.js` sixty seconds and receipts are waited on for forty, after which the reply carries the hash and says not to tap again. Tests: "delivered twice is acted on once", "two function instances over one store", "never sent twice".

### F7 · Medium · The faucet was check-then-act, unbudgeted, and one nonce for everyone

A burst of taps paid several times; nothing bounded the day's total but the faucet's own balance; every instance signed from the same key with no ordering, and a failed send threw out of the handler.

**Fixed:** the stamp is claimed atomically with the previous value given back if nothing was sent; a per-UTC-day budget across everyone (`BOT_FAUCET_DAILY_ETH`, default 0.5); a store lock around the send and a per-instance queue; failures are caught and reported. Tests: "three taps, one payout", "the second wallet waits for tomorrow", the store's budget contract.

### F8 · Medium · A custom amount could trade the wrong token

The prompt's meaning lived in a per-instance map; a reply answered on another instance, or after a cold start, fell back to the default token and bought it with the user's amount.

**Fixed:** the prompt names the token (or the withdrawal address) in its own text, which Telegram returns in `reply_to_message`; a prompt without one trades nothing and says so. Tests: "names the token", "answered on the other".

### F9 · Medium · Buttons over Telegram's 64-byte limit

`w:<address>:<amount in ETH with 18 decimals>` was 65+ bytes for any real balance, and user-typed presets and custom amounts rode unbounded; Telegram refuses the whole message, so the withdraw step silently never appeared.

**Fixed:** amounts travel as wei (a 0.05 ETH buy is 62 bytes with the token address), withdraw shares as `w:h:<to>` and `w:a:<to>` computed at tap time, presets bounded to ten characters, and both `btn()` and the test recorder throw on anything over 64 bytes, so every test enforces the limit.

### F10 · Medium · The Neon schema was one multi-statement query

Neon's HTTP driver runs the extended protocol, which takes exactly one command per request; the bootstrap would have failed on the first call and the rejected promise was cached for the instance's life. Confirmed on PGlite: "cannot insert multiple commands into a prepared statement".

**Fixed:** one statement per query, a failed bootstrap is retried on the next call, and the whole store contract runs against a real Postgres in the test suite.

### F11 · Medium · Configuration that failed quietly

No `DATABASE_URL` gave every instance its own wallets; a malformed `BOT_FAUCET_ETH` or `DATABASE_URL` threw inside `getBot()` and every update answered 500, which Telegram retries forever; internal error text (with whatever a database error carries) was sent to the user.

**Fixed:** the store is required (`BOT_MEMORY_STORE=1` allows memory on one machine, and says so in the log); every malformed variable is a refusal with its reason, answered 200 so Telegram stops; users see the chain's own words for a chain failure and a plain line for anything else. `bot-runtime.test.ts`.

### F12 · Medium · Copy that overclaimed

The fleet card said "the chain cannot" link deposit and fleet and "nothing links the deposit to them", beyond FR-015; the Sessions card linked a page that is not on this branch; mainnet was described in the present tense; Help told users to press a Faucet button the card did not have; `/pool` called draws "fleets funded"; "recovery confirmed" described a button the bot does not offer.

**Fixed:** the fleet intro is FR-015's sentence; Sessions says the contract and page are on their way and not live; mainnet is "next, not live" everywhere; the Faucet button exists when a faucet key does and the text follows; `/pool` says "draws opened"; the create reply says what is true (keys sealed here, commitment held by the service).

### F13 · Low · Chain adapter details

The swap deadline came from the last block's timestamp, which on an idle Orbit chain can be minutes old; a receipt wait that timed out lost the hash; a transient RPC failure was cached as symbol "?" and 18 decimals for the instance's life; the ERC-20 approval to Permit2 used `2^160-1` (uint96-allowance tokens revert) and both approvals were re-sent as a pair whenever either was short.

**Fixed:** deadline from `max(block, wall clock) + 600`; `pending` results with the hash; metadata cached only on success; `maxUint256` for the ERC-20 approval and each approval sent only when short. The fork test now asserts the ETH actually returned on a sale and runs a second sale with no approvals.

### F14 · Low · Smaller things

Group commands addressed to other bots (`/pool@other`) were answered; `drop_pending_updates` ran on every setWebhook; referral codes had no uniqueness constraint (a 32-bit collision credited two users with each other's referrals); deposit was offered on deployments with no pool address; the `no key bytes in the clear` test looked for a hex string inside base64 and could not fail; the self-referral test passed for the wrong reason; the fake fleet service never recomputed the payload hash.

**Fixed:** all of them. Codes have a unique index and Start steps to the next code on a collision.

## Accepted, with a note

- **`quoteExactIn` assumes one full-range position.** The venue's pools are seeded full-range by `FleetPoolSeeder`; on a concentrated pool the quote can diverge from the fill, and the user's slippage guard is what protects the trade. Noted in `market.ts`.
- **`MIN_GAS_RESERVE` is a constant**, 0.0005 ETH: 600k gas at 0.83 gwei, some eighty times the testnet base fee. It is not derived from the live fee; if the chain's fee ever rose past that, trades would fail on gas and say so.
- **The service forgets un-activated campaigns across instances.** That is the service's memory store, not the bot's; the bot works around it (one tap, start over). It stays on the service's list (T040).
- **Telegram redelivery after a killed function.** The update id is claimed before the work; if Vercel kills the function mid-trade, the redelivery is dropped and the user sees no reply. The alternative (a second trade) is worse; the receipt wait is forty seconds so it should not happen.

## What the operator still has to do

Vercel environment: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET` (16+), `BOT_USERNAME`, `BOT_KEY_SECRET` (32+, twelve distinct characters, then never changed), `BOT_FAUCET_PRIVATE_KEY` (a throwaway), `DATABASE_URL` (a Neon database; the tables are created on first use), optionally `BOT_FAUCET_ETH`, `BOT_FAUCET_DAILY_ETH`, `FLEET_POOL_ADDRESS`, `FLEET_TOKEN_ALLOWLIST`. Then `node scripts/bot-set-webhook.mjs` once with the same secret. The bot refuses to run with any of the required ones missing and says which in the log.
